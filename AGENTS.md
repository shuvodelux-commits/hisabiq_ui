1. **`/super-build` is REQUIRED for every implementation.** Read and follow the actual installed `.agents/skills/super-build/SKILL.md` and its relevant adapter reference *before writing code*. Use one of these two truthful, supported routes:

   - **No fallback without Super Build:** If neither valid route is executable, **STOP/mark BLOCKED**, identify the missing skill/launcher/runner or authorization, and keep the issue/PR unmerged. Do not replace the required skill with ad-hoc shell commands while reporting compliance.

2. **Tests are MANDATORY and are a standing owner authorization.** Write and maintain executable automated tests for **every affected business rule, branch, state transition and practical scenario** before or alongside implementation (test-first/TDD where applicable); this includes bug fixes and integration adapters. The previous R-0 rule `NEVER write test files / NEVER run test suites` is **superseded for HisabIQ work**. No separate per-chat test approval is required for this scoped standing rule. Tests must be meaningful assertions, not test-name inventories or mocked success.
3. **Complete scenario matrix per task:** enumerate each applicable happy path, validation/invalid input, boundary/rounding, missing/denied/inactive source, role/permission, cross-tenant RLS, state/version conflict, concurrency, idempotent retry/lost response, timeouts/failures/rollback, and UI keyboard/touch/mobile/accessibility path. 4. **Run the tests, not just write them.** Choose suitable unit, domain, transport/contract, integration, real disposable PostgreSQL/RLS/concurrency, and Playwright browser E2E tests, plus TypeScript/lint/build/boundaries/UI-contract checks. Mock external login only when explicitly documented; mocks never substitute for required real API/DB financial or source assertions. Do not reuse production/development databases or another worker's test tenant. Verification must use exact pinned repository SHAs, isolated GitHub branch/worktree, disposable credentials, and separately controlled test resources.
5. **Evidence and merge gate:** Each task issue/PR must map **business scenario → test file/case → actual result**, show exact executed commands, exit codes, CI run, paired source SHAs and any known gaps. A blocked/unrun, flaky, skipped or failing required scenario means **NOT VERIFIED / NOT MERGE-READY**, even if lint, build or generic CI passes. Correct the source and retest on the exact new head through Super Build. Independent QA, security/accounting review and owner merge approval remain mandatory; do not claim deployment or success from a draft PR.
6. **Existing in-flight tasks also comply.** In particular, MOD-008 P5D [PR #503](https://github.com/shuvodelux-commits/hisabiq_ui/pull/503) must be rerun through a valid Super Build route and must complete its genuine source-backed browser/DB acceptance before being declared ready. # HisabIQ UI — Mandatory Agent Rules

**UI refinement protocol (owner decision 2026-11-05):** Before any visual or motion refinement, read [UI-REFINEMENT-RULES.md](docs/ui/UI-REFINEMENT-RULES.md). The workflow is source-code-first (copy the explicitly approved reference's actual behavior/motion, not invented approximations), one GitHub draft PR per target, Playwright before/after screenshots including open interaction states, official Impeccable detector, bounded three-round review with a closing check, full regression gates and explicit human merge approval. The approved Sabab SIS navigation presentation is a targeted exception to the earlier HisabIQ-only-navigation precedent; **reuse HisabIQ business routes, permissions, UI tokens and real workflows**. This does not authorize other redesigns.

Before designing, generating, implementing, polishing or reviewing any UI, read the [complete HisabIQ Design Guide](docs/ui/HISABIQ-DESIGN-GUIDE.md). Map each element to its actual shared source; use the guide's states, tokens, Bangla, accessibility and responsive rules. [AI handoff](docs/ui/AI-UI-PROMPT.md) is the portable instruction; [generated inventory](docs/ui/design-system.json) lists current exports/files/icons. Regenerate guide data with `node scripts/sync-design-guide.cjs`; verify with `--check`. Inventory is not a visual-conformance certificate. This guide consolidates the binding contracts below; current explicit user decisions and narrower current contracts retain priority.

This file applies to the entire repository, all pages, PRs, and AI-generated UI changes. Read [UI Design & Transaction Cart Contract](docs/ui/transaction-cart-design-contract.md) **before** modifying any screen, reusable component, or product transaction workflow.

## Non-negotiable design authority
1. **Magic Patterns export and existing HisabIQ design tokens are the visual authority.** Use existing React/TypeScript and shared shadcn-style primitives (`Input`, `Button`, `Dialog`, `AppSelect`, themed date controls, etc.). Never create a competing design system or one-off field styling when a shared primitive exists.
1a. **36px standard controls; 48px terminal transaction CTAs.** Read [the Control Contract](docs/ui/2026-10-23-component-size-consistency-audit.md) and [Magic Patterns Brand Realignment](docs/ui/2026-10-25-magic-patterns-brand-realignment.md). Use `--erp-control-height` (36px) for ordinary buttons, inputs, filters, date/number/select triggers and icon actions in all modules and languages. Use `--erp-workflow-action-height` (48px) only for explicitly marked major completion/review CTAs (`data-erp-workflow-action="complete"`), e.g. POS sale, purchase and sales return. Color, `size="lg"`, or Save/Cancel status never imply 48px. Keep internal/compound controls functional; do not add page-local 40/44px sizing hacks.
1b. **Products is the table typography authority:** 13px main data, 12px column headings, 11px helpers and badges across tables and responsive rows. Read [the Table Typography Contract](docs/ui/2026-10-24-table-typography-contract.md). Reuse shared Table, mark native tables with `data-erp-table`, and identify supporting text with `data-table-helper`; preserve current weights, colors, spacing and 36px controls.
2. **POS V2 cart is the behavioral and visual authority for every product-transaction cart**: Sales/POS, Purchases, Quotations/Estimates, Online Sales, Sales/Purchase Returns, Opening Stock, replacement/service parts, stock movement and future modules.
3. **Import and reuse actual shared components and helpers.** Never copy/paste a page-local approximation of POS `Add product`, inline cart editor, searchable dropdown, unit switch, quick-add, split payments or product rows. If a context differs, extend a reusable component with semantic variants (`sale | purchase | quote | online | return`) and callbacks, not forked markup.
4. **Product selection must be searchable** (not a plain `AppSelect`/`FormSelect` listing products): one input/dropdown assembly; supports Bangla and English names, keyboard Up/Down/Enter/Escape, touch selection, focus return, clearable query, stock/price/unit/category, and a shared **Quick Add Product** path. Keep the add-product entry position consistent with the approved POS inline-cart pattern; do not move it to a different location per module.
5. **Every editable cart uses shared interaction rules** for line numbering, quantity, compound large+small units (e.g. `2 Box 5 Pcs`, `1 Gauge 12 Gira`), price in selected unit, line total, contextual row actions, reorder when applicable, discount and accurate preview amounts. Keep user-input source unit, conversion, keyboard/touch behavior and errors consistent. No monospaced numbers.
6. **Context-specific business rules may differ; visuals and controls must not.** Purchase price/lot/supplier differ from Selling price/stock/customer; Quotation is non-posting; Online order uses delivery/COD; Returns validate prior quantities. POS is the reference **UI**, not a license to reuse wrong finance/stock posting logic.
7. **Payment-capable flows** use the POS-style multiple Cash/Bank/MFS rows, conditional account selectors, total/Paid/Due, discount and rounding; source-specific permissions and accounting remain correct. Quotations do not accept real payments by default; if they show deposit terms, distinguish planned from actually received.
8. **Forms, filters and overlays**: use shared inputs, search combobox where search is needed, select for short fixed lists, shared popovers, Dialog/AlertDialog, compact Tables, accessible labels/focus/validation, standard color tokens in light and dark, Bangla helpers. Date spans use the shared date-range picker. Do not manually style arbitrary native selects/dropdowns to imitate shadcn.
9. **No cosmetic-only functionality.** Menus, dialogs, actions, empty states, buttons and modals must work at the intended UI-preview level. Never imply stock, payment, customer ledger, courier or SMS posting without real backend integration.
10. **Before PR review**, compare changed flows side-by-side with POS V2 and Purchase Cart at desktop and mobile sizes, keyboard and touch, light and dark. Verify search, addition, quick create, unit selection, quantity and price, reorder where applicable, payment, errors, keyboard focus and print order. Add/update Playwright tests.

## ERP-wide KISS: complete work inside the current module (mandatory)

Read [ERP Context-Complete Workflow Contract](docs/superpowers/specs/2026-10-09-erp-kiss-contextual-workflows-design.md) and [ERP Source Audit](docs/ui/erp-workflow-audit-2026-10-09.md) before building or declaring any module complete.

- **Context over navigation:** A module's detail workspace must handle its common related actions. Customer → selected invoice/print/edit/payment/refund/return/new sale; Supplier → bill/payment/return; Expense → payee/category/account creation/receipt/edit; Products → category/brand/unit creation. Use a shared full editor via contextual drawer/overlay/returnTo rather than duplicating posting code. Global module navigation is for optional advanced work, not mandatory frequent entry.
- **Quick Add everywhere a dependency may be missing:** Searchable selector with an integrated + New action, short shared dialog, duplicate check, tenant-scoped mutation, immediate auto-select, keyboard/focus return, and exact parent-draft preservation. Nested Category/Brand/Unit additions stay inside the New Product flow; New Payee and Expense Category stay inside New Expense.
- **Dense yet simple:** Frequent actions and relevant balance/stock visible; uncommon settings in expandable Advanced; compact tables with action menus; bilingual helpers only where useful; one clear primary action; keyboard and touch first.
- **Full action means real operation:** List every dropdown/menu/button/filter and connect it to an actual editor, mutation, readable preview, export/print or intentional disabled state with reason. `toast('Edit dialog')` is not Edit; `toast.success('Payment recorded')` without a payment record is a **P0 defect**; uncontrolled filters are broken functionality. Never make a decorative “Complete return” claim.
- **Source integrity:** Posted invoices, stock movements and ledger events require source-linked permission-aware correction/reversal with audit reason, impact preview and idempotent posting. Do not delete ledger projections or invent backend posting. Preserve Party role isolation, invoice source, selected date range, filter and scroll.
- **Same shared controls:** Actual reusable combobox/QuickAddSelect/CompoundQuantityInput/action menu/date-picker/payment rows, Magic Patterns design tokens and dark/light; do not introduce local lookalikes.
- **Acceptance:** Before PR, demonstrate 3 routine next actions from the record, Quick Add inside a half-filled form, filtered table changes, every action's outcome, keyboard/mobile/dark/light and source-safe reverse/correction. Include a per-action workflow matrix and Playwright tests; clearly mark any UI-preview-only result.
- **Priority:** Remove misleading fake financial actions and inert dropdowns before cosmetic polish. Do not rewrite the entire ERP at once; use independent, dependency-ordered slices and Superpowers approval/review gates.

## Known divergences — not approved precedent
- POS `src/components/pos/{CartTable,ProductCombobox}.tsx` is current reference.
- Purchases `src/components/purchases/{PurchaseCart,PurchaseProductSearch}.tsx` follows POS style but duplicates some picker logic; consolidate into shared primitives, **do not duplicate it again**.
- Draft PRs for Quotations and Online Sales initially use page-local `AppSelect` product pickers and different cart rows. These are **migration debt**, not reusable patterns. See [migration inventory](docs/ui/transaction-cart-design-contract.md#existing-gap-inventory-and-migration-order).
- Source code must be the same **component family**, not just similar CSS. If missing, build/refactor a shared component before shipping a new product entry screen.

## PR acceptance
- Explicitly name which shared cart/picker/input/quick-add components were reused. List and justify any exceptions; do not silently create new patterns.
- Add regression tests; document any pre-existing legacy exceptions in the contract and remove them as part of migration.
- CI runs `npm run check:ui-contract`. It blocks new page-local product dropdowns while grandfathering only currently identified draft-page violations. Do not expand the exception allowlist to make new work pass.
- Keep changes KISS. No mass visual redesign of unrelated pages in a feature PR. Do not merge without user approval.
