# HisabIQ MOD-007 M7-03 — Connected Sales Draft create/resume protocol (design, 2026-11-15)

**Why:** Existing POS V2 already has complete Hold/Resume/Edit/Duplicate preview UX, but `/app` connected routes are intentionally closed because their product, settings, party and cart sources are still fixtures. The first production-facing prerequisite is a reliable authenticated non-posting wire protocol and retained create intent, not a replacement POS screen.

**Source authority:** owner-approved parent [UI #572](https://github.com/shuvodelux-commits/hisabiq_ui/issues/572), child [UI #577](https://github.com/shuvodelux-commits/hisabiq_ui/issues/577); frontend base `hisabiq_ui/main@4a8c5bfc27aa18ebfbf52046d3ee63e70c938cad`, backend draft [#221](https://github.com/shuvodelux-commits/nestshererp/pull/221) head `7aa04ede86bb9e4b223b4e84b24cf1c5de78295d` and merged backend [#162](https://github.com/shuvodelux-commits/nestshererp/pull/162).

## Options considered
1. Connect `Pos.tsx` directly to `GET/POST/PUT` and bypass `ConnectedWorkspaceGate`: **rejected**. Preview carts, fake IDs and demo balances would be promoted to live tenant state.
2. Add a new parallel POS UI: **rejected**. Duplicates product search, multi-unit, cart, keyboard and payment controls; violates the existing design authority.
3. **Selected:** implement a strict, unmounted frontend wire adapter and an immutable in-memory create intent. Use these from the existing POS V2 after its real source bridge and connected workspace approval land. This avoids redesign and keeps lost-response safety testable now.

## Public interfaces and safety contract
- `src/integration/sale-draft-writes.ts`: `saveSaleDraft(accessToken, payload, operationId, signal?, timeoutMs?)` is exactly one authenticated `POST /api/v1/sales/drafts` with valid ULID `Idempotency-Key` header; `readSaleDraft(accessToken,id,...)` is exactly one GET; `updateSaleDraft(accessToken,id,{...payload,expectedVersion},...)` is exactly one PUT. The existing GET list `readSaleDrafts` remains in `sales.ts`.
- The request JSON has exactly `label,customerName,itemCount,grandTotalMinor,cart`; PUT adds `expectedVersion`. Preserve nested JSON cart opaque, with a defensive round-trip clone. Reject unsafe numbers, prototype poison keys, cycles, getters, data URI attachments, sparse arrays and oversized (>120k JSON characters) payloads. No decimal taka conversions, no client-generated server IDs, no tenant ID fields in DTO, no automatic network retry, no session recovery inside transport.
- An eight-key create response is decoded with the existing `decodeSaleDrafts`; a ten-key detail/update response adds `version,updatedAt`. Strictly check returned detail/update ID matches requested ID and updated version increments by one. Missing, fake, foreign or mismatched responses are protocol failures, not sample data.
- `src/integration/sale-draft-intent.ts`: secure (crypto) ULID operation key, memory-only WeakMap storing frozen JSON and tenant+user+auth epoch+token identity, permission `sale.invoice.create`. A `PreparedSaleDraftCreate` exposes only `operationId`. A deliberate resubmit of the **same handle** preserves the exact payload/key. No automatic retry, credential storage, cross-tenant replay or silent new key after a lost ACK.
- Before `prepareSaleDraftCreate` accepts the snapshot, an explicit `ConnectedSaleDraftSources` set from verified tenant catalog and customers must match the session tenant. Cart schema `hisabiq.connected.pos.draft.v1`, `sourceTenantId`, `lines[].productId` must be valid ULIDs present in the verified set; `customerId` is null or in the verified customers set. The cart's other fields (independent unit prices, conversions, bundles, serials, warranty, expiry, split/partial payments, installments) are not normalized or dropped. This is a draft-only provenance guard, not confirmation that a future sale can post.
- Scope ends at safe protocol and intent. **Do not** mount it in `Pos.tsx`, `Sales.tsx`, `App.tsx` or `ConnectedWorkspaceGate` in this PR. Do not expose DELETE or misrepresent hard delete as Recycle Bin. Backend #221, #223, runtime role verification and the live UI/catalog gate remain separate merge prerequisites.
