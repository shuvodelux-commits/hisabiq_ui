## How to read this ledger
Rows show **PR #274 proposed state** for the five status flags (not the old implementation). Flags: yes / no / partial / unverified / n/a. *Displayed* and *editable* do not prove saving; *persistent* means current **browser settings provider**, not cloud; *consumed* means actual end-user UI or draft reads the value; *enforced* means operational/security policy, **never inferred** from a local toggle. An honest `none found` means **not found in reviewed consumers**, not a definitive whole-repository absence. `browser-working` does not imply server authorization. P0 is user-trust/security/accounting risk, P1 business workflow, P2 polish/discovery.

**Super Review correction:** `browser-working` in this inventory means the preference is saved locally and its consumer has been traced in source. It does **not** mean an end-to-end browser test or backend enforcement has passed. Where a consumer could not be traced, readiness remains `unverified` even if the editor can save. Only executed behavior tests prove the end-to-end workflow.

The original typed `src/settings/fields.ts` catalogue contains **60 ordinary fields**, plus separately implemented specialized workflow controls. Actual supported feature source is `src/settings/model.ts` and `src/settings/TenantSettingsProvider.tsx`; all business settings still use a demo tenant ID and browser persistence. PR #274 restores live saves for ordinary fields, but many policy consumers remain disconnected.

## Findings that affect priority
- **P0:** Magic Users/Roles, Data/restore, and Staff Activity remain simulation surfaces. There is no authenticated server authority or live multi-tenant data backup in these versions.
- **P0:** Invoice default reset in PR #274 updates `numbering.sale.prefix` while `prefix` is not in its visible generic `settingsFields.invoices` list, making previously customized prefixes fail validation. See separate PR review.
- **P0:** `money.lockDate`, `money.adjustment`, `invoices.showPurchaseCost`, VAT configuration and notification transport are not proven enforced at transaction/server boundaries.
- **P1:** The new Product editor consumes several defaults via `initialProductDraft`, but `priceEntry`, `openingUnit` and `minimumUnit` are not read there. Do not claim a value is applied merely because it saves.
- **P1:** PR #274's POS Guardian/Phone/Address controls and Purchase memo/photo controls are real UI consumers, but require backend tests for the business rules they touch; invoice output has two simultaneous editors.
