# Proposed additive contract amendments

These names and algorithms are **PROPOSED**, not endpoints or columns that exist in either baseline. This file resolves narrow engineering seams whose business intent is already clear. It deliberately leaves unresolved accounting policies in DECISIONS.md blocked. No migration may be executed from this document.

Verified issue: existing `MyAccessResponse` returns user, businessName, permissions and features; it does **not** return tenantId or timezone. `GetMyAccessService.execute(ctx)` has tenantId in verified TenantContext; its timezone may be the token-time snapshot. Read the live business profile for bootstrap timezone. The frontend cannot namespace live caches from a fabricated `t1`.

**Existing endpoint:** GET `/api/v1/me`; request remains empty, existing TenantContextGuard. **PROPOSED response addition:** required `tenantId: string` canonical ULID and `timezone: string` validated IANA timezone, alongside all existing fields. No new permission, mutation, journal, idempotency or audit event. Existing errors remain 401 for unauthenticated / existing service NOT_FOUND for disabled/missing user. No caller tenant argument.

**MODIFY backend:** `packages/core-contracts/src/auth.ts::myAccessResponseSchema`; `packages/core-application/src/auth/get-my-access-service.ts::execute` returns `tenantId:ctx.tenantId, timezone:profile.timezone`. Replace its name-only `TenantRepository` dependency with existing `BusinessProfileRepository` from `settings/settings-repository.ts`; call `findProfile(tx,ctx)` in the same read UOW, return `profile.businessName`, and reject missing profile with existing NOT_FOUND. In `apps/api/src/registration/registration.module.ts`, replace the GET_MY_ACCESS_SERVICE factory's TenantRepository argument/TENANT_REPOSITORY injection with BusinessProfileRepository/BUSINESS_PROFILE_REPOSITORY (the token already exists in infrastructure/tokens). Preserve other providers and their TenantRepository usage. `apps/api/src/registration/me.controller.ts` retains `{data: ...}`. Search all MyAccessResponse consumers, typed mocks and strict response decoders; add the two fields to actual fixtures without relaxing checks. **MODIFY frontend:** FOUNDATION SessionProvider maps `data.tenantId`, `data.user.id`, `data.timezone`; no JWT decoding establishes authority. Preserve the existing `/me` permission semantics and fields.

**Tests:** existing login/users API tests plus proposed `apps/api/test/me-bootstrap.spec.ts`. A/B token requests return their own tenantId/timezone, never body/query-supplied values. Missing auth never returns cached identity. Change tenant timezone, authenticate afresh: server timezone appears; bootstrap does not mutate settings/audit/journal. Frontend rejects missing new fields until deployed compatible API is available. Deploy backend addition before frontend consumers; old frontend can ignore additive properties if its decoder permits, and strict same-repo schemas update together.

## EXT-02: Bengali master names and unit symbols

**Existing endpoints:** catalog units create/rename/list, product create/edit/get/list. **PROPOSED fields:** Unit request `{name:string,nameBn?:string|null,symbol?:string|null}`; Unit response `{id,name,nameBn:string|null,symbol:string|null}`. Product save/update adds `nameBn?:string|null`; product response adds `nameBn:string|null`. Existing other product fields remain required as in SaveProductRequest. This is not yet the multi-unit chain contract.

Validation: name uses existing catalogNameSchema; nameBn trim, blank→null, max120 for unit and max200 for product, Unicode allowed; symbol trim, blank→null for legacy rows, 1–4 nonwhitespace characters when present (same intent as validUnitSymbol). New HisabIQ unit UI still requires its symbol; legacy APIs remain backward compatible. Omitted on edit preserves stored value; explicit null clears only that field. Preserve original unit identity/name keys and all historic document wording. A symbol/nameBn change cannot alter conversion factors, stock or any posted unit snapshot. Do not introduce arbitrary symbol uniqueness: two units may share shorthand while their IDs remain distinct; UI must resolve selection by ID.

**Exact backend file responsibilities:** core-contracts `catalog.ts` and `products.ts`; domain `catalog/catalog-name.ts` (additional text/symbol validation without changing existing name key); application `catalog/manage-catalog-service.ts`, `catalog/catalog-repository.ts`, `catalog/manage-products-service.ts`, `catalog/product-repository.ts`; adapter `catalog-repository.ts`, `product-repository.ts`, `schema.ts`; one coordinator-reserved migration adding nullable text columns to tenant units/products. Controller methods keep existing routing/response envelope; pass new fields explicitly. Update audit before/after payload and existing view mappers without secrets. Old rows backfill null; no rename or regenerated key.

**Frontend:** `src/data/productUnits.ts` remains display-helper source; connected mode obtains server master metadata instead of mutating seed arrays. `useAddProductForm.createUnit/editUnit/save` await named adapter calls. Render `nameBn`/symbol while retaining current hover/focus edit behavior. New typed integration view metadata carries server master IDs. Posted invoice unit names must be snapshotted by the later transaction extension before that workflow is cut over; live rendering from today's master is insufficient.

**Mutation class:** M; existing permissions and catalog/product service audit pattern. No journal/stock movement. Existing create idempotency behavior stays endpoint-specific. **Acceptance:** edit `Gauge` symbol `Gg`, Bangla `গেজ`; product ID, factors and stock remain identical. Invoice already posted continues its old wording. Omitted old-client fields preserve existing metadata. Null explicitly clears only permitted metadata. Foreign-tenant unit edit not-found; no side effects. Concurrent rename semantics remain existing repository behavior and must not be falsely called version-protected if they are not.

## EXT-03: purchase split and receiving atomicity — scoped proposal, not ready for dispatch

Existing createPurchaseRequest accepts paidMinor/paidAccountCode, line expiryDate, correctionOf and no correctionVersion. UI one confirm includes multiple accounts, serial text, lot selling price, batch/manufacture metadata and attachment. This amendment needs D06/D16 approval and exact source trace before dispatch.

Proposed additive input: `payments?: readonly {accountCode:string;amountMinor:number}[]` (1–10 positive safe integer poisha entries when present); `correctionVersion?:number` positive when correctionOf is present; line `serials?:readonly string[]` (max500, trimmed1–64, unique by existing serial rules), `lotSellingPriceMinor?:number|null` nonnegative, `batchNumber?:string|null` max120, `manufactureDate?:YYYY-MM-DD|null`. Existing expiryDate remains. If payments is supplied, reject nonzero legacy paidMinor or nonnull paidAccountCode to prevent double posting; absent payments uses unchanged legacy path. No computed total accepted.

Algorithm required inside `CreatePurchaseService.createWithin`: permission/idempotency/period → lock source if correction and compare version before reversal → validate all real supplier/product/account/serial identities and dates → calculate exact domain total and per-account paid sum → resolve every account and aggregate repeated account outflow before checking balance → receive lots and serial rows via composable in-transaction methods → persist purchase and all payment allocations/journal lines → audit/outbox → durable response. Any validation/audit/outbox failure rolls back all rows. A correction reverses original allocations/serial links in the same UOW and retains source provenance. Null lot selling price means use product default; product override flag wins if enabled, per existing HisabIQ requirement.

**Still incomplete:** numeric line-price representation for independently priced unit chains (D16), authenticated attachment storage contract, existing serial composability and schema-column types/constraints, complete class-T correction locking, and exact provider wiring for new repository methods. These must be resolved in the amendment, not by the future coding agent. No new POST endpoint is proposed; no half-built typed stub may ship.

## EXT-04: transaction-aware optional cash sessions — owner requirement confirmed

The blanket financial-transaction gate is superseded by [CASH_SESSION_POLICY](../tasks/CASH_SESSION_POLICY.md). Historical party/lender/borrower opening balances do not require an active session. Existing customer/supplier openings already follow this behavior through Opening Equity. Lender/borrower openings are new backend capability work, not existing partyRole support.

Actual designated-drawer receipts/payments require an eligible open session when ON and return sessionId:null when OFF. Bank/MFS-only and other non-drawer operations do not become session-gated. Ordinary credit sale, unpaid purchase/expense and stock-only changes do not require cash merely because a journal is posted. A backdated payment is not an opening and a client cannot send a historical bypass flag.

The linked policy specifies the existing ten payment-account callers, direct money/correction checks, proposed CashSessionPolicy class, lock ordering and concrete tests. Pending PR16 provides a candidate shared SettingsRepository.lockTenant/history guard but remains unmerged; it does not change payment-account.ts. Caller/provider manifests and source correction details must still be completed against the selected approved source SHA before dispatch. No new public cash endpoint or bypass field is required.
