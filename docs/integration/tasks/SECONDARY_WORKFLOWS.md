# Additional existing-service integration traces

These are precise reusable API seams, with current gaps named. They supplement the module packets and do not authorize a full module build until its gap matrix is complete. All CREATE files below are proposed. All tests are future specifications, not executed results.

## ACC-01 — account identity and statement

**UI:** `/app/accounts`, `src/pages/Accounts.tsx`; current finance-account fixtures and local state. **CREATE:** `src/integration/accounts.ts`. **Existing backend:** `apps/api/src/money/accounts.controller.ts` → `ManageAccountsService` for list/create/update/deactivate; `DailyCashService.statement` for statement → `PostgresMoneyRepository`. Tables accounts/account_openings/journal_entries/journal_lines, source movements. Current balance is ledger-derived, never assigned from the UI.

`GET /api/v1/money/accounts` uses AccountListQuery and returns MoneyAccountListResponse (`accounts`, not generic `data[]`). Statement `GET /money/accounts/:id/statement` uses AccountStatementQuery and actual AccountStatementResponse. UI row ID→real id; name→name; Cash/Bank/Mobile Banking map to actual type CASH/BANK/MFS; do not infer account type from a string prefix. Use exact `createMoneyAccountRequestSchema`, `updateMoneyAccountRequestSchema` (including version) and deactivate body `accountVersionRequestSchema`. Opening fields may post journal; treat initial account opening as its existing owning service, not a generic balance write.

Keep existing Accounts tabs, add/edit dialog, bank-entry launch and print controls. Selecting an account loads its statement and clears prior account response only when new result is confirmed; abort old request. Search and date filters use the existing server keys. A foreign/missing account response does not display the prior account's ledger under the new title. Repeated account labels remain distinct IDs. BankEntry stays blocked until every type has an actual accounting mapping.

**Proposed tests:** `tests/integrationAccounts.test.ts`, `scripts/integration-accounts-browser.cjs`, existing backend `cash-day.spec.ts` relevant account cases. Test name `account statement is ledger authority`: bank opening100000 + receipt25000 − supplier payment30000 → balance95000 with those source rows; rename account leaves balance/journal untouched; stale update409 preserves draft; another tenant's account is unreadable; account without permission omitted as existing contract specifies.

## REC-01 — bank statement upload and matching

**UI:** `src/pages/Reconciliation.tsx::UploadStatementDialog`, `updateSelectedStatus`, `matchSelected`; current upload dialog explicitly says PDF reading is not connected. **CREATE:** `src/integration/reconciliation.ts`. Existing backend `money/reconciliations.controller.ts` → `ReconcileAccountService`, `ImportStatementService` → reconciliation repository/statement extractor; tables account_reconciliations, bank_statement_files, statement_lines, reconciliation_matches; ledger rows refer to journal_lines.

Start POST `/api/v1/money/reconciliations` body `{accountId,fromDate,toDate,operationId}`. Upload POST `/:id/statement` body `{fileName,contentBase64}` (not MIME/hash fields invented by client); server validates actual bytes/format. Result is StatementPreviewResponse per controller envelope. Display `parseStatus`, lines and problems in existing dialog structure, preserving entered edits; unreadable is not empty-success. Confirm POST `/:id/statement/confirm` body `{fileId,lines,openingBalanceMinor,closingBalanceMinor}`. Each line: lineNo, businessDate, description, reference/null, signed amountMinor (in positive/out negative), balanceMinor/null, editedByUser. Do not multiply signed amount twice when rendering direction.

Match POST `/:id/matches` body `{statementLineId|null,journalLineId|null,state}`; at least one side required. Remove uses DELETE `/:id/matches/:matchId`. Complete POST `/:id/complete` body `{statementClosingBalanceMinor,note|null,version}`; reopen POST `/:id/reopen` `{reason,version}`. Fetch workspace after successful mutation so server differences/outstanding decisions display. Do not map Ignored to REJECTED without resolving D18. `ErpEditor` cannot edit a reconciliation projection; use documentType/documentId/documentVersion and its owning source editor, then reload workspace. No balancing entry is silently created.

**Proposed tests:** `tests/integrationReconciliation.test.ts`, `scripts/integration-reconciliation-browser.cjs`; reuse backend reconciliation/reconciliation-pdf suites. `upload unreadable leaves draft unchanged`; `signed statement amounts survive mapping`; `same journal line cannot be matched twice where prohibited by actual match rules`; `complete stale version changes nothing`; `editing source triggers its correction and requires rematch`; `foreign fileId unreadable`; `remove match preserves statement and original journal`; `bank mismatch does not create new money movement`. Exact complex match/ignored business cases remain D18.

## WAR-01 — serial provenance and warranty

**UI:** `src/pages/Warranty.tsx` new-case save, updateCase, sendExternal and source-linked actions. **CREATE:** `src/integration/warranty.ts`, `serials.ts`. Existing controllers: SerialsController (`/serials`) and WarrantyController (`/warranty-claims`) are separate classes in one file. Reuse SerialService/WarrantyService and owning repositories; no UI-generated serial IDs. UI print receipt remains current renderer.

Serial record POST `/api/v1/serials` `{purchaseLineId,serials:string[]}` → SerialProgressResponse; available GET `/serials/available/:productId` yields inventoryUnit IDs; lookup GET `/warranty-claims/lookup?serial=...` or phone/invoiceNumber yields ClaimCandidateResponse. New claim POST `/warranty-claims` uses productId, inventoryUnitId|null, saleId|null, customerPartyId|null, customerName, customerPhone|null, complaint, handling SHOP/COURIER, courierName|null, receivedDate. Existing `WarrantyCase.issue` maps complaint only after original source selected. Route labels are not permission grants.

Move POST `/warranty-claims/:id/move`, header Idempotency-Key, body MoveWarrantyClaimRequest: status, settlement|null, note|null, replacementUnitId|null, recoveryMinor|null, recoveryAccountCode|null, businessDate, version. Replacement is an actual stock operation, and source accounting through WARRANTY_EXPENSE remains authoritative. D17 blocks lossful UI status conversion; do not hide Waiting supplier/Received from supplier/Ready for customer or mark completion because backend status is merely SETTLED. Temporary replacement has no demonstrated equivalent in the move DTO and needs its own approved contract.

**Tests:** `tests/integrationWarranty.test.ts`, `scripts/integration-warranty-browser.cjs`; approved backend spec location must be determined because no standalone warranty.spec.ts exists in current API test inventory. Case `replacement consumes exact authorized inventory unit once`: duplicate click/key does not consume twice; foreign serial/sale rejected; source warranty snapshot stable after current product warranty edit; zero recovery does not become null unknown; status version conflict leaves claim/stock/journal unchanged. Missing state/provisional replacement tests cannot be invented until D17.

## DAY-01 — daybook and contextual correction

**UI:** `src/pages/Daybook.tsx::updateFilters`, source review overlays; `AuditLedger.tsx` remains a separate financial review surface. **CREATE:** `src/integration/daybook.ts`, `audit.ts`. Existing GetDaybookService/MarkDayReviewedService/PrintDaybookService; list may join several source tables, but Daybook does not own their monetary mutations.

GET `/api/v1/daybook` exact query keys `from,to,dateBasis,kind,partyId,userId,accountCode,cursor,limit`; dateBasis BUSINESS_DATE default or CREATED_AT with server permission. Use response `actions` for enabled source actions; pass identity and version to owning source editor. Business vs entry date must not be renamed into one generic date. `POST /daybook/review` and `/daybook/print` use their linked actual schemas; print history GET `/daybook/prints`. Existing operational print is allowed; no new Reports generation engine.

Audit GET `/api/v1/audit-events` returns security/business audit data; it is not a substitute for Daybook financial balances. Do not allow deleting audit events. Shared source correction/date mutation uses source service and returns to same filter/scroll/selection. Server accounting totals remain independent of visible page.

**Tests:** `tests/integrationDaybook.test.ts`, `scripts/integration-daybook-browser.cjs`; existing backend corrections.spec.ts/audit.spec.ts. On a backdated receipt, BUSINESS_DATE and CREATED_AT views place it on their respective days; user lacking entry-date permission cannot reveal it. Review/print annotation adds no journal/stock. Void/correct source records its owning reversal, changes relevant display and retains immutable prior history; failed correction preserves original source and current dialog.

## DBH-01 / SEARCH-01 — operational cards and search

**UI:** Dashboard MetricCard/RecentSalesTable/DuesList and GlobalSearch. **CREATE:** `src/integration/dashboard.ts`, `search.ts`; MODIFY data consumption in the existing components, not their chart markup/layout. Existing `/dashboard/summary`→GetDashboardSummaryService gives businessName. `/dashboard/cards`→DashboardService→ReportRepository returns permission-filtered operational amounts; no new report endpoint is proposed.

Map todaySalesMinor to today's sales only; cashInHandMinor→cash, bankBalanceMinor→bank, customerDueMinor→customer dues, supplierPayableMinor→supplier payable, lowStockCount→low stock, stockValueMinor only with cost access, todayProfitMinor with profitProvisional label. Use response businessDate. Missing fields are unavailable, not0. `recentSales[].id/number/customerName/grandTotalMinor/createdAt` preserve actual source link. D15 blocks trend/cashflow graph data parity and incomplete dues widget fields, while current widget layout/customization remains.

Global search `GET /api/v1/search` uses actual GlobalSearchQuery and response source identifiers. Replace `globalSearchRecords` only for live mode. Match text and arrows/Enter result focus remain current; debounce/abort, discard results from previous tenant/epoch/query. Backend permission filtering must also omit forbidden cost/profit/name details. Do not search fixture arrays after a failed live request.

**Tests:** `tests/integrationDashboard.test.ts`, `tests/integrationSearch.test.ts`; proposed browser `scripts/integration-dashboard-search-browser.cjs`. With profit permission removed after load, refresh omits profit rather than retaining stale amount; no forbidden data in serialized body. Summary endpoint is never treated as financial metrics. A slower query A response cannot replace later query B; selected result opens actual source and preserves query on return. No writes to reports/schema/source financial tables for either read.
