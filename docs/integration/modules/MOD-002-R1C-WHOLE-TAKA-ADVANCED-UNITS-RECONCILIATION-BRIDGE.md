## 2. Source-to-ledger chain: non-negotiable shape, pending allocation algorithm

1. **Product master — Class M (future R2/R3):** persist a tenant-owned, immutable *published profile revision* with ordered stable unit IDs and exact cumulative conversion factors. Record each independent purchase/sell override separately; **missing/null ≠ explicit zero**. Hide confidential purchase overrides entirely from a cost-blind API response, including replay/error/audit paths. An old full-body edit must not erase new fields.
2. **Cart request — present UI, future R4 backend:** keep ordered components such as **1 Box + 5 Pcs**, each original selected unit ID, entered decimal qty and exact *own-unit* sell/buy rate or explicit default-derivation source, and revision ID. No approximation to a base-unit price merely to satisfy legacy \`products.sellingPriceMinor\`.
3. **Stock identity:** compute canonical base quantity from a frozen rational factor. Existing backend base-stock scale is 3, so any input that is not *exactly* representable at this scale must be refused **without rounding stock** until a separate quantity-scale policy is approved.
4. **Unrounded financial source:** compute the price of each component with bounded exact arithmetic; calculate line and bill discounts against source-known amounts. If a 4dp master unit rate times fractional entered quantity yields sub-poisha amounts, **the conversion/quantization boundary is still a D16 decision**, not implied by #55's final-taka policy. Do not apply whole-taka rounding to the master rate, each component or each line.
5. **Single final rounding — APPROVED:** after the authorized discount pipeline yields an exact validated *pre-final amount in integer poisha*, compute \`postedObligationMinor = roundWholeTakaMinor(preFinalNetMinor)\` **once per new invoice**. Then \`finalRoundingDeltaMinor = postedObligationMinor - preFinalNetMinor\`. This formula is conditional on a separately approved pre-final sub-poisha quantization policy; #55 does not establish that earlier boundary.
6. **Source allocation — NOT YET APPROVED:** allocate (a) discounts, then (b) final whole-taka rounding difference across original lines/priced segments under a deterministic, source-owned and reconstructible rule; retain original unrounded price/qty and resulting *posted* segment/line monetary shares. **Sum of final source shares must equal header and journal exactly.** Do not invent a balancing sales line, silently change COGS, or allocate the customer rounding delta into inventory valuation by accident.
7. **Money/journals:** customer/supplier due, advances, payment sources and invoice posting must use the frozen rounded obligation. Accounting \`ROUNDING\` posting (if applicable) is an **explicit, balanced, auditable financial line**, separate from the approved inventory/lot cost accounting and not a fake Product/cart line. Its exact debit/credit design, invoice share adjustment and cancellation handling require the independent accounting approval specified in #55.
8. **Returns:** reference the *original posted priced segment and source line*, not current Product price/factor/name. For incremental return value and COGS, reconcile against the **actual cumulative previously booked source monetary credits** within the same locked source UOW, bounded by the original posted share; never use a fresh estimate for already-booked money. This has to preserve zero-৳ positive-qty source reversal Option A and its stock/cost semantics.
9. **History/offline:** old posted documents (fractional whole poisha, old no-round/৳5 rules, source labels, historic discounts and original lot costs) are immutable and must retain their *own frozen* policy version. Offline one authorized device must carry original profile and rounding-version identity; reject an old ambiguous writer rather than reinterpret old source under new rules.
10. **Read path:** existing POS V2 ProductCombobox/CartTable and backend \`GLOBAL_V2\` search are not a complete advanced-unit Product read model. React→Nest read-only browser QA [merged PR #450](https://github.com/shuvodelux-commits/hisabiq_ui/pull/450) proves tenant/standing/search only; it **does not** prove a mixed-unit source sale, actual return or correct posting.

## 3. Concrete deterministic vectors — review examples, NOT executed implementation tests

All examples are in BDT. They demonstrate required invariants / unsafe alternatives. They are **not** a claim that current backend posting achieves these outputs.

| Case | Validated arithmetic / proposed consequence | Safety significance |
|---|---|---|
| Independent prices | 1 Box (20 Pcs) at **৳232.25/Box** + 5 Pcs at **৳12.50/Pcs** = **৳294.75** before discounts; canonical stock issue **25 Pcs** | Do not derive Box price as 20×Pcs or flatten to one base price |
| Final rounding after discount | ৳294.75 gross − ৳10.40 discount = **৳284.35**; final new obligation **৳284**, delta **−৳0.35** | Preserve the 35-poisha reconciliation source; do not leave header, line shares and journal unequal |
| Component rounding is wrong | Two separately priced components at ৳0.50 each: exact pre-final net **৳1.00** → **৳1**. Rounding each component to ৳1 first produces **৳2** | Whole-taka must be **once at final invoice**, not once per Box/Pcs or per line |
| Order of discount matters | Gross ৳100.50 − discount ৳0.49 = ৳100.01 → **৳100**. Premature gross rounding makes ৳101−৳0.49=৳100.51 → **৳101** | Discount first, **then** final round |
| Returned only Pcs | From the *no-discount* Box+Pcs invoice above: final obligation **৳295**. Five Pcs' original raw amount was ৳62.50, but a refund/credit of **৳62.50 or ৳63 cannot be asserted** without the agreed source allocation of the invoice's **+৳0.25** delta | Store original priced segment and allocated posted share; never infer refund from today's catalog or 5/25 of combined line |
| Repeated return cap | Original **৳3** payable across 5 identical Pcs, returned 1 Pcs each time. Naive independent \`round(3/5)\` credits ৳1 five times → **৳5** (wrong). One possible illustrative cumulative target sequence is [৳1, ৳1, ৳2, ৳2, ৳3], increments [৳1, ৳0, ৳1, ৳0, ৳1] → ৳3 | This is a counterexample/illustration, **not** an approved allocator; actual previously booked values and source caps govern |
| Stock-only zero amount | A positive-qty sourced return can have **৳0 incremental obligation/credit** after allocated rounding; source-linked stock/lot/cost reversal must still be handled under approved Option A | Do not reject a valid stock return merely because customer monetary value is zero; do not create synthetic cash |
| Quantity representability | If a future 4dp input is authorized: 0.0001 Box ×10 Pcs/Box = 0.001 Pcs (scale-3 valid); ×3 Pcs/Box = 0.0003 Pcs (scale-3 invalid) | No silently rounded stock quantity |
| Price / cost boundary | ৳0.0001 per Pcs ×100 Pcs = ৳0.01 exact *before* any final invoice rounding; at low value the new whole-taka obligation may be zero | R1-A sub-poisha master and minimum-charge policy remains open; do not silently label positive-priced stock as free |
| Historic amount | Old invoice posted at **৳100.35** remains **৳100.35**, not repriced to ৳100 or ৳101; returns are anchored to its frozen monetary source | No global setting rewrite or destructive conversion of existing obligations |

**Money conservation to prove before any production wiring:**

- \`finalObligationMinor % 100 === 0\` on every **new** sale/supplier invoice; **legacy** invoice policy and posted value remain frozen unchanged.
- \`sum(postedLineNetMinor) === finalObligationMinor\`, and \`sum(postedSegmentNetMinor) === postedLineNetMinor\` where advanced segments exist. If an explicit accounting rounding-difference posting is also present, journal debits and credits must balance and must **not double count** the same delta in revenue/cost/receivable.
- \`sum(all actual posted returnValueMinor for source segment) <= original posted sourceSegmentNetMinor\`; at full return, amounts reconcile to the source net **under the approved residual policy**, not the current Product's prices. Cost/COGS and inventory source caps are **separate** invariants.
- \`paymentsApplied + dueChange + advanceOrChange\` must reconcile to the original *frozen* rounded document obligation per the approved payment/accounting direction; cash-session ON/OFF eligibility is not affected by historical opening balances.
- For every booked stock movement, \`sum(segments.baseQty3) === sourceLine.baseQty3\` and owned/vendor/negative lot-source allocations match the source issue/return without an extra movement from rounding.
- After logout/tenant change, stale state or an idempotent replay must not expose cost fields or mix tenant/actor permissions.

## 5. Ordered, separately authorized implementation gates

1. **G0 — Finance source correctness FIRST:** independent backend #55 and return #36 review, reconcile open draft PRs [UI #437](https://github.com/shuvodelux-commits/hisabiq_ui/pull/437), [backend #54](https://github.com/shuvodelux-commits/nestshererp/pull/54) and source-return remediation gate [UI #392](https://github.com/shuvodelux-commits/hisabiq_ui/pull/392). None of these drafts is a completed live posting feature. Freeze final total-rounding pipeline, explicit signed rounding-difference accounting and return caps; ensure double entry, partial/multiple payments, due/advance, refunds and cash-session behavior remain sound. No simultaneous shared money or posting editor.
2. **G1 — Advanced-unit business decisions:** owner/accountant signs **remaining** D16-P1/Q1/D1/S1/Z1/C1/L1 and intermediate piece of D16-R1 (including sub-poisha quantization, source delta allocation, zero-value new sales and return policy). Document whether temporary selected-unit prices may exceed 4dp when deriving exact rational rates. This doc provides recommendations and examples, **not approvals**.
3. **G2 — Legacy conversion evidence:** a separately authorized non-production snapshot census under [R0-A](MOD-002-R0A-LEGACY-CONVERSION-CENSUS-PLAYBOOK.md) or synthetic-only feasibility check; do not query real tenants by default. Select R1-B storage approach A/B only after old base-relative conversion integrity and active Product profiles are understood.
4. **G3 — Explicit R2 SQL + command approval:** adopt a versioned, tenant-owned immutable source profile (candidate R1-B design), add stable cost-redacted reads, permission-safe scoped edits, published revision locks, migration RLS/FK, legacy closed-writer policy, durable audit/outbox and idempotency; test on **isolated disposable PG16**, no real tenant data. Keep legacy simple Product endpoints unchanged for compatible products.
5. **G4 — Source transaction / return correctness:** implement paired sale/purchase/return priced segment snapshots and original allocation IDs; bind source net/line/header/journal and stock/COGS. Prove arithmetic/property vectors, concurrent source locks, stale version, revoked role, cost privacy, negative/owned/vendor inventory and repeated fractional/historical returns. Offline device policy and explicit source rounding-version must be proven.
6. **G5 — React integration last:** connect existing HisabIQ Product full-page Add/Edit, shared ProductCombobox/CartTable, purchases and POS V2 **only after** exact backend contract supports all independently priced levels and historical snapshots. Preserve keyboard loops, 36px controls, 48px final actions, Bangla helper text, drafts, split tender, serial/warranty/expiry, Bundle, shortage choices. Do not unlock global \`ConnectedWorkspaceGate\` prematurely.

**Release/rollback:** old posted invoices must stay readable/returnable under original frozen rounding rule; after advanced postings start, do **not** roll back by dropping profile/segment tables or coercing advanced products to one old unit. Block old API/offline writers that cannot preserve source revisions; provide monitoring and a separately approved reversible feature rollout. No destructive Product Delete.
