> **P0 ERRATUM — 2026-11-13 (supersedes earlier return-rounding guarantees in this document):** Source-based arithmetic review found that [current sales-return `shareOf`](https://github.com/shuvodelux-commits/nestshererp/blob/54eb8fd1bd4e9ca7e8a389a8b299615b39c6535a/packages/core-domain/src/sales/sales-return.ts) and [purchase-return `billedShare`](https://github.com/shuvodelux-commits/nestshererp/blob/54eb8fd1bd4e9ca7e8a389a8b299615b39c6535a/packages/core-domain/src/purchasing/purchase-return.ts) can over-credit an original source line after repeated separately rounded partial returns. ## Executive conclusion

**No current backend contract can losslessly accept HisabIQ's multi-level product unit chain and independent per-unit purchase/selling prices.** This is a **source-verified incompatibility**, not an objection to the existing one-conversion implementation for its own clients.

- Migration `0008` created **`product_unit_conversions`** for multiple per-product conversion rules, with an active-row uniqueness index and RLS. Migration `0010` deliberately **left** it intact while adding the single-conversion pair to `products`; it backfilled **only products having exactly one active conversion row**. Products with multiple old rows were not flattened and their old rows were retained. This is important recoverable historical evidence, but **current rows/counts are unknown**.
- At the pinned commit, the compiled application source scan found `productUnitConversions` used only as a schema declaration and `product_unit_conversions` in a test reset list; the active Product repository reads/writes `products.conversionUnitId`/`conversionFactorQty`. That proves **no modeled active table reader in scanned TS sources**, not that any production table is empty or can be dropped.
- `pricePerBaseUnit()` converts an alternate-unit price to whole-poisha base-unit price using **half-up rounding**. The source explicitly documents `৳105.05 / Pipe ÷20 Feet = ৳5.2525 / Feet → ৳5.25 / Feet`, so converting back produces `৳105.00 / Pipe`, not the originally entered `৳105.05`. This cannot store a different Box price or four-decimal UI custom price accurately using only the base column.
- A current posted sale/purchase line **does** persist base-unit quantity, whole-poisha base unit price and booked totals, and sales returns use the **original line's posted net amount**, but repeated partial-return rounding **does not always reconcile** (see P0 erratum); preserve the source-value basis while correcting the allocator. What is **missing** for advanced UI parity is immutable selected-unit identity, entered unit quantity/price, conversion factor/profile version, and bilingual unit wording on each source line.
- A posted purchase currently calls `products.setPurchasePrice()` to refresh the product's **single base-unit purchase price** from the latest receipt. An advanced per-unit cost design must specify whether and how that remains compatible, especially when custom unit costs, landed costs and cost permissions differ.
- The existing one-thumbnail adapter, simple Product read/create/edit and version checks are already merged and **must remain functional for legacy-compatible products**. The rich React Add/Edit form remains **not connected**; no cost-hidden full-body update should be attempted.

## 5. Price representation and rounding — verified versus proposed

**Verified:**
- Legacy storage uses `BIGINT` minor units with base-unit `purchase_price_minor`/`selling_price_minor` and scale-3 quantity. Existing `pricePerBaseUnit` expressly rounds **half-up** on division; it is designed for the one-conversion legacy model, not arbitrary independent unit prices.
- HisabIQ's [`ProductDraft`](https://github.com/shuvodelux-commits/hisabiq_ui/blob/00d7f60b76e65936f31daa99dd9b8c1106088374/src/types/productForm.ts) and [`validCustomPrice`](https://github.com/shuvodelux-commits/hisabiq_ui/blob/00d7f60b76e65936f31daa99dd9b8c1106088374/src/utils/productDraft.ts#L47-L55) admit **up to four decimal digits BDT** for per-unit overrides, while posting totals remain whole poisha. `Number`-based frontend calculations are only form previews.
- Sales and purchase returns **attempt** to distribute residual minor units from original source net, but repeated partial returns can exceed booked values. **Block reuse of the current quantity-only residual allocator** until [backend P0 #36](https://github.com/shuvodelux-commits/nestshererp/issues/36) is resolved. Purchase reversal/lot valuation paths have their own rounding, e.g. [`CreatePurchaseService`](https://github.com/shuvodelux-commits/nestshererp/blob/d2060a7b2c9e2b364b0d0e6d5aad1d077fa76a75/packages/core-application/src/purchasing/create-purchase-service.ts#L210-L239); review all unit-cost scale boundaries together.

**Proposed for R1 review (NOT automatically accepted):**
- Stable catalog-unit IDs + explicit product unit profile version; ordered adjacent factors using canonical decimal/rational values, bounded to quantities representable at the stock scale-3 posting boundary.
- Nullable **independent** buy/sell overrides per unit. `null` means derived; explicit `0` is not `null`. Never approximate/custom-price-coerce to base whole-poisha before persisting.
- Selected-unit quantity, price (exact entered decimal), factor/profile version and frozen unit/product bilingual labels attached to posted sale/purchase/return source **in addition to**, not instead of, existing base qty/poisha booked amounts.
- A common domain rounding rule with explicit tie direction, place of rounding, discount allocation and partial-return residual reconciliation; **do not decide this from current UI's `Number.toFixed`**.
- Reject or explain a mathematically unrepresentable stock or money amount rather than silently dropping precision. Determine the policy for a valid `৳0.0001` unit price and small quantity before posting.
- Legacy product read/edit/import must be **read-through compatible or refuse editing a rich product**; it may not delete the extra levels, prices or cost fields because its DTO knows only the first pair.

**Illustrative acceptance vectors (not approved tariff):** `1 Box=20 Pcs`, `1 Carton=12 Box`, so `1 Carton=240 Pcs`; Box sell `৳232.25` may differ from `20×৳12.50=৳250.00`; Carton sell can be another override. `1 Pipe=20 Feet`, `৳105.05/Pipe` cannot round-trip through a sole whole-poisha Feet price. For 1, 2, and final partial return after a source-line discount, cumulative returned value must equal original posted line value.

## 6. Data integrity and security constraints for the next design

1. **Legacy preservation:** never delete/mutate historical `product_unit_conversions` rows until a signed data inventory and reversible migration are accepted. Current `0008` schema contains product/unit foreign keys and RLS; a new design still needs complete tenant ownership validation, revision-scoped uniqueness, FK/RLS cross-tenant negative tests and backfill idempotence.
2. **Single authority:** do not write both the old per-product table and `products` conversion pair as unsynchronized competing sources. Choose a versioned authoritative profile plus explicit safe legacy projection after real caller/data audit.
3. **No historical price rewrite:** original posted sale/purchase line totals, inventory movements, cost layers, ledger postings, source allocation snapshots and return source IDs are immutable. Only new source-linked corrections/reversals update current state.
4. **Cost security:** current `purchasePriceMinor` is absent in response without `COST_VIEW`. The merged replay security fix recomputes current cost permission; the advanced profile must do so for each per-unit cost and any cached response, tenant and user. A cost-blind edit cannot fill an omitted required value with zero.
5. **Version and offline:** source optimistic version lock; a single authorized offline POS device retains selected profile revision and original line input. Server must accept/resolve old revision deterministically before committing inventory; do not claim complete offline replay tests on this R0 audit.
6. **Purchase actual-versus-configured cost:** legacy `setPurchasePrice` refreshes base master purchase cost on each receipt. R1 must decide new per-unit configured price vs latest purchase cost vs actual landed cost; never silently overwrite a different custom Box/Carton cost.
7. **Full form preservation:** `nameBn`, unit symbols, photo gallery, optional serial mode, day-based warranties, expiry/FEFO settings, Service/Bundle kinds and opening lot metadata remain **explicitly separate D04/D06/D09/EXT-02 gaps**. No early React Add/Edit connection that silently omits them.
