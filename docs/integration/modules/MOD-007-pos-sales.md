### R3.5. Server posting, stock, immutable snapshots, accounting and permissions

**Existing ordinary-sale transaction:** `SalesController.create` checks strict request + 26-character Idempotency-Key → `CreateSaleService.create` opens `UnitOfWork.run(ctx)` → SALE_CREATE permission → period/date/customer → payment account authorization/session → policy/stock/serial/cost → pure `saleTotals`/`salePosting` → `SaleRepository.insertSale` (sale and line source, payments, journal, lots/movements/consumptions, stock cost state) → audit + one `sale.posted` outbox → persisted idempotency response → `SaleResponse`. A UOW does not prove serializable last-stock locking; **last-unit and parallel payment tests remain mandatory**.

**Guest identity invariant:** Current `resolveCustomer` reuses the system-reserved walk-in identity for an anonymous fully settled sale; it does **not** create an ordinary named customer. A selected real customer remains selected. Creating a customer is allowed only if the user expressly saves one, or the transaction requires attributable outstanding due or retained customer advance with valid identity; cash alone never mandates a new ledger person. The walk-in identity must not accept later generic customer receipts. Credit exposure and customer advance belong to the CUSTOMER role's separate journal-backed balance, not a cash checkout method.

**Stock origin invariant:** Server validates `allocations[].qty` total equals exact base quantity; owned stock, consignment/vendor lots and explicitly approved negative stock retain different source allocations and cost behavior. Server must lock stock position, sellable lots and selected serial units (or use equivalently verified serialization), enforce expiry/serial/negative/consignment policy and protect final-unit races. Do not trust React `allocatePosStock` or preview lot reservations as posting authority. Vendor shortage cost `null` must remain unknown/provisional, never coerced to a real zero. Atomic failure leaves **zero** new sale/lot/movement/serial-sale/journal/audit/outbox/receipt/operation effects.

**Historical posting snapshot contract (gap):** Freeze product/line display name (EN/BN as applicable), item kind, entered-unit ordered quantities and labels/symbols, conversion numerator/denominator/profile revision, pricing mode/rate/offer/lot override origin, base qty, server unit/gross/discount share/net, tax/rounding rules if approved, customer identity/snapshot, sale business date, source allocations/lot IDs, serial IDs/wording, warranty/expiry at sale, cost layers and resulting payment account rows in a tenant-owned immutable/versioned source representation. **Money/credit arithmetic:** `saleTotals` alone computes posted grand total/paid/due/overpayment in integer poisha. Real payment legs hit only real account codes; `CHANGE` reduces retained account payments and never becomes a retained receipt, whereas `ADVANCE` makes an attributable customer-advance liability. For later genuine money receipts, `ReceiveCustomerPaymentService.receive` takes a **single** account/amount and posts source-linked allocation to named or oldest open invoices; a refund or internal application of already-held advance is **not** another receipt. Proposed example: preexisting advance liability **30000 poisha**, open AR **20000 poisha**, apply **20000 poisha** → DR customer advance 20000 / CR customer receivable 20000, remaining advance 10000, invoice due 0, **no Cash/Bank movement**. This is a **desired test vector**, not a currently available endpoint or approved chart amendment. Customer credit refund must likewise be a source-linked cash/bank outflow under MOD-005 session policy and permission, not a negative UI number.

**Cash/session classification:** Credit sale `payments=[]`, bank/MFS-only sale, draft and a purely internal customer-credit application need **no** cash session. If a payment leg targets the tracked drawer and `cash_session_enabled=ON`, an eligible OPEN same-business-day session is required; with `OFF`, ordinary tracked-cash receipts/payments are journaled with null session ID. The inspected `resolvePaymentAccount` still requires OPEN for drawer even under OFF: this is a **MOD-005 prerequisite**; MOD-007 must not introduce a caller-side bypass.
